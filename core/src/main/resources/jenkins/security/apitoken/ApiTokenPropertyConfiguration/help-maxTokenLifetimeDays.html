The maximum number of days an API token may live, counted from the day it is created. Leave the field empty, or enter 0, for no limit. This is the default, and nothing is restricted then.

Once the limit is enforced (see Enforce the maximum lifetime from ), an API token that is created through the HTTP endpoints, which is what the user configuration page and scripted clients use, must expire within that number of days from today. A token is valid through its expiration date, so the last date that is allowed is today plus the maximum. A token that never expires is rejected. A request that does not ask for a duration gets a token that expires on the last day that is allowed, today plus the maximum; the response gives that date.

The limit only applies when a token is created. Tokens that exist already are not touched. Neither are tokens that are created from a script or from the script console through the Java API, unless Strict mode is in effect: then the maximum covers them too, and nobody is exempt. Legacy API tokens never expire, so the maximum cannot apply to them: once it is enforced, users who are not exempt can no longer regenerate a legacy token from their page, but the legacy tokens that are generated for new users (see the options above) are not limited, even in strict mode.

A maximum of less than 7 days is accepted, but then every new token is flagged as about to expire as soon as it is created.

The users listed under Users exempt from the maximum lifetime are not restricted, unless strict mode is in effect.

The compliance panel lists the tokens that exceed the maximum, which includes the tokens that never expire, and the secrets that are shared by several tokens of one user. It does so as soon as a maximum is configured, before the enforcement date too. It does not list the tokens of the users who are exempt, except while strict mode is switched on and has not started yet: they are listed then, marked with the date from which they will no longer be exempt. A banner on the Manage Jenkins page tells administrators when there is something to review. Dismissing that banner hides it for every administrator, until the monitor is enabled again under Manage Jenkins > System > Administrative monitors. The panel itself stays reachable through the link in this section.

Registering a secret again

The maximum limits tokens, not secrets. A client that chooses the value of its token itself and registers it through the HTTP endpoint ( addFixedToken ) could register the same value again before each expiration, and every registration would give it a new expiration date. So once the limit is enforced, a secret that is already registered for the user is rejected, and the client has to switch to a new secret to keep working.

  • Any token of the user with that secret counts, whether it has expired or not. So does the user's legacy token: its value, registered as 11 followed by the value, is rejected. The letter case of the hexadecimal digits does not matter.
  • Nothing changes while the limit is not enforced, that is with no maximum or before the enforcement date, and for the users who are exempt: they can register the same secret again, as before. In strict mode nobody is exempt, so the rule applies to them too.
  • Only the tokens of the same user are compared. The same secret registered for two different users gives two independent tokens, each one limited on its own. Tokens that Jenkins generates are never compared, their secret is random.
  • The rejection is answered like the other ones, with HTTP status 200 and "status":"error" in the response. A client that checks only the HTTP status does not see it, and fails later, when the token it holds expires and no longer authenticates. This is what happens to provisioning that registers the same token again each time it runs.

This is not a complete protection. Jenkins does not remember the secrets of revoked tokens: once every token that has this secret is revoked, the same secret can be registered again, so a secret can be kept alive by revoking and registering it before each expiration. The Java API, which scripts use, does not check the secrets either, unless strict mode is in effect. And the tokens that existed before the limit was enforced are not touched.
